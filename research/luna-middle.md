# Luna middle-period omission research (2005–2016)

Research cutoff: 2026-11-06. The years below mark an observable milestone (release, standard, or policy change), not necessarily origin or universal adoption. Prevalence is separated from technical availability. Cases controlled mainly by one vendor are scoped accordingly.

## Candidate decisions

| Candidate | Milestone and practice change | Prevalence / scope | Evidence and limits |
|---|---|---|---|
| Windows Vista User Account Control (UAC) | Vista (2006–07) introduced split administrator tokens, consent prompts, and standard-user compatibility measures; admin work required elevation. | Shipped broadly with Vista; no adoption measure here. User accounts and prompt settings varied, and prompts were often disabled or trained through. | Microsoft UAC overview: https://learn.microsoft.com/en-us/windows-server/security/user-account-control/user-account-control-overview ; Vista dev requirements: https://learn.microsoft.com/en-us/windows/win32/secauthz/user-account-control. Demonstrates design and availability, not rates of standard-user use or prompt effectiveness. **Recommend.** |
| Data Execution Prevention (DEP/NX) | Windows XP SP2 (2004, lead boundary) introduced hardware-backed non-executable memory policy, providing a mitigation against injected-code execution. | Hardware- and configuration-dependent; XP default was opt-in for Windows components/services, with broader modes configurable. | Microsoft DEP configuration: https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/determine-hardware-dep-available ; DEP overview: https://learn.microsoft.com/en-us/windows/win32/memory/data-execution-prevention. A sustained defense rather than a single retirement; hardware coverage and compatibility exceptions matter. **Recommend.** |
| Vista ASLR | Windows Vista (2006) added address randomization for images and system components, raising the cost of reliable memory-corruption exploits. | OS/version and image compatibility dependent; later platforms broadened coverage. | Microsoft ASLR mitigation: https://learn.microsoft.com/en-us/microsoft-365/security/defender-endpoint/exploit-protection-reference ; MS SDL guidance: https://learn.microsoft.com/en-us/security/engineering/solving-security-vulnerabilities. ASLR changes exploit reliability, not the existence of memory bugs; not every allocation was randomized. Candidate requires better period-specific adoption measurement. |
| Windows XP SP2 firewall default | XP SP2 (2004) shipped Windows Firewall enabled by default, with inbound unsolicited traffic blocked, after worms exploited always-on broadband connectivity. | Windows XP service-pack users; coverage varied by OEM, domain policy, and later configuration. | Microsoft XP SP2 overview: https://learn.microsoft.com/en-us/security-updates/security/2004 ; Microsoft 2004 partner remarks: https://news.microsoft.com/speeches/will-poole-microsoft-worldwide-partner-conference-2004/. Strong default change, but this overlaps the lead's core firewall candidate. |
| AutoRun disabled for USB mass storage | Windows 7 RC (2009) stopped AutoPlay from launching AutoRun tasks on non-optical removable media, while retaining CD/DVD behavior; Microsoft tied the decision to increasing USB malware spread including Conficker. | Windows 7 default plus a planned XP/Vista update; optical media and devices identifying as CD-ROM remained exceptions. | MSRC explanation: https://www.microsoft.com/en-us/msrc/blog/2009/04/autorun-changes-in-windows-7/ ; threat rationale: https://www.microsoft.com/en-us/msrc/blog/2009/04/changes-in-windows-to-meet-changes-in-threat-landscape. Clear response, but vendor explanation does not quantify infections prevented. **Recommend.** |
| Chromium browser sandbox | Chromium's 2008 security architecture separated browser and renderer processes and restricted renderer access to files and network resources after code execution. | Became a defining protection in Chrome/Chromium; platform-specific implementations and later browser architectures differ. | Chromium launch-era explanation: https://blog.chromium.org/2008/09/security-architecture.html ; current sandbox FAQ: https://github.com/chromium/chromium/blob/main/docs/design/sandbox_faq.md. Original post describes an intended containment boundary, not proof that all exploits were contained; sandbox escapes remain possible. **Recommend.** |
| Mobile OS application sandboxing | iPhone OS and Android shifted consumer phones toward per-app isolation, with each app constrained from other apps' data and system resources. | Broad across iOS/Android devices, but implementations differ and users/developers can grant inter-app or system-mediated access. | Android Open Source Project: https://source.android.com/docs/security/app-sandbox ; Apple Platform Security: https://support.apple.com/guide/security/app-security-overview-sec35dd877d0/web. The current Apple documentation is retrospective and Android's page does not establish the original rollout date. **Recommend with date caveat; date to verify before publication.** |
| Android runtime permissions | Android 6.0 Marshmallow (2015) moved dangerous permissions to runtime prompts and let users revoke individual grants. | Android 6+ apps targeting API 23+ use the model; legacy-target apps behaved differently until later platform policy. Fragmented handset update schedules make population-wide dates difficult. | Android 6.0 behavior changes: https://developer.android.com/about/versions/marshmallow/android-6.0-changes ; permission model guide: https://developer.android.com/training/permissions/requesting. Clear platform behavior, but availability on a released OS is not evidence every user saw or understood prompts. **Recommend.** |
| Gatekeeper | OS X Mountain Lion (2012) made the default policy allow Mac App Store apps and apps signed by identified developers, with an override and stricter option. | Default for Mountain Lion installs/upgrades; Mac owners could change settings, and the default authenticated publisher identity rather than certifying software as safe. | Apple's launch description: https://www.apple.com/newsroom/2012/06/11Mountain-Lion-Available-in-July-From-Mac-App-Store/ ; technical overview: https://www.apple.com/media/us/osx/2012/docs/OSX_MountainLion_Core_Technologies_Overview.pdf. Shows an execution default and trust mechanism, not malware-prevention rate. **Recommend.** |
| HSTS | RFC 6797 (2012) standardized a server signal for browsers to force future HTTPS connections and reject certificate errors, addressing downgrade/SSL-stripping exposure after a first secure visit. | Implemented in major browsers and used by many sites; preload lists reduce first-visit exposure for included domains. Adoption varies and HSTS cannot secure a first contact absent preload. | RFC 6797 full text: https://www.rfc-editor.org/rfc/rfc6797 ; Chromium HSTS preload FAQ: https://chromium.org/hsts/. Standard establishes mechanism and threat model; current preload page is not a dated adoption census. **Recommend.** |
| DNS transaction randomization | RFC 5452 (2009) required unpredictable source ports and strict response matching to make forged DNS replies harder after cache-poisoning attacks. | Recursive-resolver implementation change; by RFC recommendation, not a universal measured deployment date. DNSSEC is a separate complementary defense. | RFC 5452: https://www.rfc-editor.org/rfc/rfc5452 ; Kaminsky disclosure-era paper: https://www.doxpara.com/DMK_BO2K8.ppt (presentation; use RFC's cited attack discussion if slide link is unstable). Standards guidance is not evidence every resolver complied; deployment data needed. **Recommend.** |
| NPAPI / Java browser plugin removal | Browser vendors phased out NPAPI and Java applets; Chrome and Firefox removed most plugin support by 2015–17 as web APIs displaced plugin functions and plugin vulnerabilities/instability accumulated. | Major desktop browsers; enterprise and ESR exceptions delayed some deployments, and Flash followed a separate schedule. | Mozilla's 2015 roadmap: https://blog.mozilla.org/futurereleases/2015/10/08/npapi-plugins-in-firefox/ ; Firefox 52 release: https://www.mozilla.org/en-US/firefox/52.0/releasenotes/ ; Oracle JDK 9: https://www.java.com/en/download/help/jdk9_plugin.html. Clear retirement, but multi-vendor and multi-year transition. **Recommend.** |
| ActiveX control restrictions | Internet Explorer zones, prompts, signed-control rules, and kill bits narrowed the conditions under which web pages could install or run ActiveX controls. | Windows/IE-specific and policy dependent; controls remained in enterprise and legacy sites well after default restrictions increased. | Microsoft ActiveX security settings: https://learn.microsoft.com/en-us/previous-versions/windows/internet-explorer/ie-developer/platform-apis/aa751968(v=vs.85) ; MS advisory on ActiveX kill bits: https://learn.microsoft.com/en-us/security-updates/securitybulletins/2009/ms09-032. Candidate has dispersed settings rather than one clean milestone; avoid presenting the control as retired in this period. |
| SSLv3 deprecation | IETF RFC 7568 (2015) prohibited SSLv3 after years of known weaknesses and the POODLE attack sharpened operational pressure; fallback to SSLv3 was also prohibited. | Standards-level mandate adopted by browser and server vendors over subsequent releases; long-tail legacy endpoints persisted. | RFC 7568: https://www.rfc-editor.org/rfc/rfc7568 ; Chrome's POODLE response: https://security.googleblog.com/2014/10/this-poodle-bites-exploiting-ssl-30.html. Strong retirement transition; standard date is not the date every server disabled it. **Recommend.** |
| RC4 removal from TLS | RFC 7465 (2015) required clients and servers never to negotiate RC4 cipher suites after practical statistical attacks undermined confidence in it. | TLS ecosystem; deployment depended on client/server updates and legacy compatibility. Later TLS 1.3 omitted RC4. | RFC 7465: https://www.rfc-editor.org/rfc/rfc7465 ; RFC 8446 TLS 1.3 suite definition: https://www.rfc-editor.org/rfc/rfc8446. Standard tracks prohibition, not actual fleet compliance; distinguish from MD5 hashing and from protocol-version retirement. **Recommend.** |
| MD5 deprecation in signatures | RFC 6151 (2011) said MD5 was no longer acceptable where collision resistance is required, particularly digital signatures, following collision research and certificate demonstrations. | Cryptographic guidance; actual use persisted in non-security checksums and compatibility systems. | RFC 6151: https://www.rfc-editor.org/rfc/rfc6151 ; rogue CA certificate research: https://www.win.tue.nl/hashclash/rogue-ca/. RFC explicitly preserves some checksum/HMAC cases; this is not a claim that all MD5 use ended. Lead has SHA-1; keep this distinct and likely omit from public set unless concise taxonomy helps. |
| Certificate Transparency | Following certificate authority failures including DigiNotar (2011), Google engineers developed public certificate logs; RFC 6962 (2013) specified auditable append-only logs and browser enforcement made certificate issuance more visible. | Chrome and other ecosystems adopted CT requirements for selected certificate classes; not every certificate or client had identical coverage. | RFC 6962: https://www.rfc-editor.org/rfc/rfc6962 ; Chrome CT policy: https://googlechrome.github.io/CertificateTransparency/ct_policy.html. Transparency aids detection and accountability; it does not prevent issuance or prove every log entry was promptly audited. **Recommend.** |
| Browser site isolation | Chrome 67 (May 2018) enabled Site Isolation by default on desktop after Spectre raised the risk of cross-site data leakage through speculative execution; pages from different sites were separated into sandboxed processes. | Desktop Chrome rollout, with platform and memory constraints; Android rollout was later and more limited. | Chromium Site Isolation: https://www.chromium.org/Home/chromium-security/site-isolation/ ; Chromium Q2 2018 update: https://www.chromium.org/Home/chromium-security/quarterly-updates/. Specifically a response to a class of side-channel and process-boundary risks, not a complete Spectre fix. **Recommend.** |
| Shodan searchable device index | Shodan (launched 2009) made exposed service banners and devices searchable, changing reconnaissance and defenders' ability to inventory public exposure. | Public internet services and users; coverage follows scans and banner parsing, not a complete or real-time census. | Shodan's own About page: https://www.shodan.io/about ; Shodan developer API: https://developer.shodan.io/api. Dual-use discovery tool; do not say it caused attacks or treat its index as all exposed devices. Good contextual candidate, weaker direct response chain. |
| ZMap high-speed scanning | ZMap research (2013) showed a single-port IPv4 scan could complete in roughly 45 minutes, changing the scale and time cost of Internet-wide measurement. | Research technique and later ecosystem; scan speed depends on ports, bandwidth, filtering, and target response. | USENIX Security paper: https://www.usenix.org/conference/usenixsecurity13/technical-sessions/paper/durumeric ; project documentation: https://zmap.io/. Scanning is dual-use and the study establishes measurement capability, not causation for exploitation waves. Include as context only. |
| DNSSEC deployment | DNSSEC was standardized to authenticate DNS data after cache poisoning and response forgery concerns, adding cryptographic signatures and chain validation. | Root signed in 2010; deployment and validation grew unevenly across TLDs, resolvers, and stub clients. | RFC 4033: https://www.rfc-editor.org/rfc/rfc4033 ; root signing ceremony/rollout: https://www.icann.org/resources/pages/dnssec-2012-02-25-en. Broad defense with substantial rollout lag; avoid implying universal client validation. |
| SSLv2 retirement | RFC 6176 (2011) formally prohibited SSL 2.0, long after stronger protocols had superseded it, as legacy compatibility kept weak handshakes available. | Standards and vendor implementations; long-tail servers remained configurable. | RFC 6176: https://www.rfc-editor.org/rfc/rfc6176 ; TLS protocol history in RFC 7568: https://www.rfc-editor.org/rfc/rfc7568. A clear standards retirement, but may duplicate SSLv3 for public storytelling. |
| Internet Explorer Protected Mode | IE7 on Vista (2006) ran Internet-facing browser processes at low integrity, limiting writes to protected system areas after web-based code execution. | Vista/IE platform and configuration specific; later browser sandbox designs broadened the approach. | Microsoft IE Protected Mode overview: https://learn.microsoft.com/en-us/previous-versions/windows/internet-explorer/ie-developer/platform-apis/aa969736(v=vs.85) ; IE7 security architecture: https://learn.microsoft.com/en-us/archive/msdn-magazine/2006/november/internet-explorer-7-security-part-1. Strong implementation detail but overlaps browser sandbox entry; could be a platform-specific companion. |
| Java applet sandbox tightening | Java deployments added signed-code prompts and later security-level settings requiring explicit approval for unsigned/unknown applets as browser-based exploitation intensified. | Oracle Java versions and browser configurations; enterprise exceptions persisted. | Oracle Java Control Panel security levels: https://www.java.com/en/download/help/jcp_security.html ; Java SE 7u51 changes: https://www.oracle.com/java/technologies/javase/7u51-relnotes.html. Primary documentation supports default changes, but attribution across incidents needs care and plugin retirement is a cleaner endpoint. |
| iOS code signing / App Store gate | iPhone OS required signed code and distributed ordinary apps through Apple's App Store starting in 2008, creating a centralized review and update channel. | iOS ecosystem; jailbreaking and enterprise/sideload paths qualify the boundary. | Apple Platform Security: https://support.apple.com/guide/security/app-security-overview-sec35dd877d0/web ; Apple Developer Program history: https://developer.apple.com/support/compare-memberships/. Security benefit and review effectiveness are contested and layered with sandboxing; high prevalence but avoid equating review with malware elimination. |
| Android verified app sandbox | Android's Linux UID model isolated apps from the first releases, making per-application process separation a baseline security property. | Broad Android deployment, but shared UID and explicit IPC/access grants create exceptions. | AOSP sandbox documentation: https://source.android.com/docs/security/app-sandbox ; Android security overview: https://source.android.com/docs/security/overview. Current docs describe enduring design, not first-release historical detail; pair with contemporaneous Android 1.0 docs before publication. |
| ASLR in mainstream Windows | Windows Vista (2006) randomized image load locations; Windows 7 and subsequent releases expanded ecosystem support while compilers and applications adopted the mitigation. | Windows platform; executable opt-in and compatibility characteristics shaped coverage. | Microsoft Exploit Protection reference: https://learn.microsoft.com/en-us/microsoft-365/security/defender-endpoint/exploit-protection-reference ; Windows Vista security feature overview: https://learn.microsoft.com/en-us/windows/security/threat-protection/overview-of-threat-mitigations-in-windows-10. Good long transition, though exact default scope varies by executable and version. |
| UAC virtualized legacy writes | Vista redirected some legacy applications' writes from protected locations to per-user virtual stores, allowing more software to run without full admin rights. | 32-bit, non-elevated legacy apps under specific conditions; not a universal least-privilege solution. | Microsoft UAC virtualization: https://learn.microsoft.com/en-us/windows/win32/sysinfo/user-account-control-virtualization ; UAC overview: https://learn.microsoft.com/en-us/windows-server/security/user-account-control/user-account-control-overview. Useful evidence of compatibility pressure shaping security design; probably a detail within the UAC entry. |
| HTTP Strict Transport Security preload | Browser vendors began shipping HSTS preload lists so initial visits to listed sites could start in HTTPS without relying on a prior header. | Major browsers, opt-in domains only; list requirements and support differ by browser. | Chromium preload FAQ: https://chromium.org/hsts/ ; HSTS specification: https://www.rfc-editor.org/rfc/rfc6797. Addresses first-visit downgrade gaps for listed hosts only; enrollment is not a general site census. |
| Secure transport policy hardening (RC4 and SSLv3) | Standards moved from permissive protocol negotiation to explicit MUST NOT requirements for SSLv3 and RC4 between 2014–15. | Browser/server vendors implemented on different release schedules; legacy systems delayed enforcement. | RFC 7568: https://www.rfc-editor.org/rfc/rfc7568 ; RFC 7465: https://www.rfc-editor.org/rfc/rfc7465. Can be told as one transition only if both milestones and independent causes remain visible; avoid flattening cipher and protocol weaknesses. |

## Recommended public candidates

The clearest omissions to add are DEP, UAC, AutoRun, Chromium sandboxing, Android runtime permissions, Gatekeeper, HSTS, DNS query hardening, NPAPI/Java removal, SSLv3 and RC4 retirement, Certificate Transparency, and Chrome Site Isolation. Mobile sandboxing is important but the origin date needs contemporaneous documentation. Shodan/ZMap add a useful visibility thread only if paired with actual defensive inventory or measurement outcomes; their availability did not cause exploitation. The lead's browser-facing HTTPS, SHA-1 certificates, Flash, and later incidents should retain their separate entries to avoid conflating adjacent transitions.
