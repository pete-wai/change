# Luna omission research: recent shifts (2017–2026-11-06)

Research cutoff: 2026-11-06. Candidate strength reflects documented change plus scope, not a claim that a threat disappeared. I opened the relevant vendor/standards pages and checked whether dates were rollout, enforcement, GA or planned milestones. Vendor adoption figures below are labeled as such. The lead researcher owns final selection and independent review.

## Strong candidates

| ID / candidate | Previous practice, pressure, response and observed outcome | Date, reach and limits | Primary evidence |
|---|---|---|---|
| SMBv1 removed from clean Windows installs | SMBv1 remained a Windows file-sharing compatibility option despite newer SMB dialects. WannaCry and other worms made legacy SMB exposure costly. Microsoft stopped including it by default in Windows 10/Server version 1709, with edition and upgrade differences; current Windows 11 clean installs omit client and server. SMBv2/3 remain. | 2017 rollout; Windows editions differ, in-place enterprise upgrades may retain it, and it can be reinstalled on some versions. Strong evidence of a default shift, not universal retirement. | https://learn.microsoft.com/en-us/windows-server/storage/file-server/Troubleshoot/smbv1-not-installed-by-default-in-windows (complete current behavior and caveats); https://learn.microsoft.com/en-us/windows-server/storage/file-server/troubleshoot/detect-enable-and-disable-smbv1-v2-v3 |
| Exchange Online Basic Auth disabled | Clients repeatedly sent stored passwords to Exchange endpoints; password spray and stolen credentials put legacy protocols at risk. Microsoft moved tenants toward OAuth/Modern Auth and disabled Basic Auth across several Exchange Online protocols. It is now disabled in all tenants and cannot be re-enabled. | Rollout began Oct 2022; completed in all tenants, with protocol scope and consumer Outlook.com excluded. Cloud service only; on-prem Exchange and other mail providers are separate. | https://learn.microsoft.com/en-us/lifecycle/announcements/basic-auth-deprecation-exchange-online ; https://learn.microsoft.com/en-nz/exchange/clients-and-mobile-in-exchange-online/deprecation-of-basic-authentication-exchange-online |
| Passkeys become a mainstream sign-in option | Passwords can be phished, reused and stolen. FIDO/WebAuthn platform credentials let a device screen lock authorize a site-specific public-key credential. Google made passkeys the default suggested sign-in method on supported devices; Google reported over 1 billion sign-ins across 400 million accounts by May 2024. | Google default prompt Oct 10 2023; 400M Google accounts and 1B authentications by May 2024. Those are company-reported counts, not all accounts using passkeys or an industry adoption rate. Password fallback remains. | https://developers.googleblog.com/en/passkeys-week-is-here/ ; https://blog.google/innovation-and-ai/technology/safety-security/google-passkeys-update-april-2024/ ; https://fidoalliance.org/passkeys/ |
| Mandatory 2FA for GitHub code contributors | Developer account takeover can turn trust in a maintainer into malicious source releases. GitHub progressively required 2FA for developers contributing code, prioritizing groups with supply-chain reach. GitHub reported 95% enrollment among contributors notified in 2023 and a 54% increase in 2FA use among all active contributors. | Rollout March–Dec 2023, reported March 2024. GitHub-specific population and company-reported results; participation/coverage is not universal and enforcement occurred in staged groups. | https://github.blog/news-insights/product-news/raising-the-bar-for-software-security-github-2fa-begins-march-13/ ; https://github.blog/security/supply-chain-security/securing-millions-of-developers-through-2fa/ |
| PyPI makes 2FA mandatory for all account actions | Stolen maintainer credentials allow altered package uploads. PyPI moved from voluntary 2FA and targeted requirements to requiring every account to enroll before management actions or uploads. Current PyPI documentation says 2FA is mandatory. | Effective Jan 1 2024 for all PyPI users/projects; package browsing and installs do not require an account. API tokens and trusted publishing provide automation routes. Narrow to the Python package registry, not every package ecosystem. | https://blog.pypi.org/posts/2023-12-13-2fa-enforcement/ ; https://docs.pypi.org/about/security-and-internals/ |
| IMDSv2 adds a session-token barrier against SSRF | Cloud apps often expose temporary instance-role credentials through a link-local metadata endpoint. A server-side request forgery can reach it. AWS introduced IMDSv2, requiring a PUT-created token for metadata access, and has since made it default/required on selected new launch paths and instance types. | Introduced Nov 2019; Quick Starts IMDSv2-only in Nov 2023; new instance types IMDSv2-only by default from mid-2024, but administrators can enable IMDSv1. Existing instances unaffected without migration. AWS-specific. | https://aws.amazon.com/blogs/security/defense-in-depth-open-firewalls-reverse-proxies-ssrf-vulnerabilities-ec2-instance-metadata-service/ ; https://aws.amazon.com/blogs/aws/amazon-ec2-instance-metadata-service-imdsv2-by-default/ ; https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/instance-metadata-transition-to-version-2.html |
| Gmail turns sender authentication into delivery requirements | Forged sender identities and unauthenticated bulk mail made phishing/spam difficult to filter. Google required authentication from senders to personal Gmail and stronger aligned SPF/DKIM/DMARC, unsubscribe and spam-rate compliance for bulk senders. It reports a 75% drop in unauthenticated messages after its earlier baseline requirements; rejection enforcement ramped Nov 2025. | Feb 2024 requirements; Nov 2025 rejection ramp. All senders to personal Gmail have baseline obligations; over 5,000 messages/day has added requirements. Google controls its inboxes, not all email delivery; enforcement is phased. | https://blog.google/products-and-platforms/products/gmail/gmail-security-authentication-spam-protection/ ; https://support.google.com/mail/answer/81126 ; https://support.google.com/mail/answer/14229414 |
| Office ActiveX controls disabled by default | Office ActiveX content could run interactive code embedded in documents and was used in malicious attachments. Microsoft now disables ActiveX controls by default in Microsoft 365 and Office 2024; users can still enable them through Trust Center. | Documented for Microsoft 365 / Office 2024 and Windows desktop Office; legacy behavior and policy management vary. This is a default change, not removal of ActiveX or a universal block of all document code. | https://support.microsoft.com/en-us/office/vba/activex-controls-are-disabled-by-default-in-microsoft-365-and-office-2024 ; https://support.microsoft.com/en-us/excel/add-or-register-an-activex-control |
| Chrome Site Isolation in response to Spectre | Browser tabs historically shared renderer processes across site boundaries to save resources; Same Origin Policy bugs and speculative execution could expose cross-site data. Chrome made site-per-process isolation the desktop default and later extended isolation on Android to logged-in sites on eligible devices. | Chrome 67 desktop (2018); Android Chrome 77 (2019) for signed-in sites on devices with at least 2 GB RAM. Memory cost limits mobile scope; browser-specific mitigation, not a Spectre fix at hardware level. | https://www.chromium.org/Home/chromium-security/site-isolation/ ; https://www.chromium.org/developers/design-documents/site-isolation/ ; https://security.googleblog.com/2018/07/mitigating-spectre-with-site-isolation.html |
| npm trusted publishing replaces long-lived CI tokens | Long-lived package publish tokens can be stolen from CI and abused to alter releases. npm added OIDC trusted publishing so authorized CI workflows obtain short-lived credentials and automatically attach provenance attestations. | npm GA July 31 2025 for GitHub-hosted Actions and GitLab shared runners; private-source provenance remains unavailable, and adoption has no published ecosystem-wide rate. Feature availability is not mainstream adoption. | https://github.blog/changelog/2025-07-31-npm-trusted-publishing-with-oidc-is-generally-available/ ; https://docs.npmjs.com/trusted-publishers/ |
| npm classic publishing tokens revoked | npm classic tokens were long-lived and broad; compromised credentials could publish or administer packages. After a staged change, npm disabled classic-token creation, capped new write-token lifetimes, permanently revoked classic tokens in December 2025 and moved interactive logins to two-hour sessions. Bypass-2FA granular tokens still serve some CI workflows, and further restrictions announced for 2027 remain future. | Enforced on npm registry accounts; maintainers had to update local and CI workflows. This does not affect GitHub tokens or other registries. | https://github.blog/changelog/2025-09-29-strengthening-npm-security-important-changes-to-authentication-and-token-management/ ; https://github.blog/changelog/2025-12-09-npm-classic-tokens-revoked-session-based-auth-and-cli-token-management-now-available/ ; https://github.blog/changelog/2026-07-31-restricting-npm-bypass-2fa-granular-access-tokens/ |
| TLS 1.0/1.1 browser retirement | Older TLS versions have design weaknesses and lack modern cryptographic options. Browser makers gave site operators notice, measured use and then disabled the versions by default. Firefox 78 and Chrome 84 shipped the change in 2020; pandemic conditions delayed the initial schedule and Firefox temporarily restored support earlier that year. Browser release notes confirm the eventual action. The evidence supports a browser transition, not universal removal from all software. | Firefox 78 shipped June 30, 2020; Chrome removal shipped in version 84 after a delay. Mozilla reported TLS 1.1 on 0.1% of connections in 2018; remaining legacy servers could cause connection errors. | https://blog.mozilla.org/security/2018/10/15/removing-old-versions-of-tls/ ; https://www.firefox.com/en-US/firefox/78.0/releasenotes/ ; https://hacks.mozilla.org/2020/06/new-in-firefox-78/ ; https://security.googleblog.com/2019/10/chrome-ui-for-deprecating-legacy-tls.html ; https://blog.chromium.org/2020/02/ |
| Google and Android move new low-level work toward memory-safe code | C/C++ memory errors remain a major source of exploitable bugs. Google has publicly made memory-safe languages a strategic direction and is applying Rust incrementally to firmware, prioritizing new and high-risk code while hardening legacy C++. | Google statements in 2024 document direction and projects, not cross-industry adoption or a completed migration. No global standard/default changed; strong ongoing transition case only if final collection accepts partial practice changes. | https://security.googleblog.com/2024/03/secure-by-design-googles-perspective-on.html ; https://security.googleblog.com/2024/09/deploying-rust-in-existing-firmware.html ; https://security.googleblog.com/2024/10/safer-with-google-advancing-memory.html |
| Android revokes permissions from unused apps | Users often grant apps access to sensitive data and then stop using them, leaving permissions active. Android 11 added automatic reset of runtime permissions for apps unused for several months and one-time grants for location, camera and microphone. | Android 11 (2020); Google expanded auto-reset to older supported devices in 2021. Exceptions and user controls remain; applies to runtime permissions. | https://developer.android.com/about/versions/11/privacy/permissions ; https://support.google.com/android/answer/9431959 |

## Examined candidates, rejected or deferred leads

Checked against primary sources: items 1–2 and 5–10, plus 14–15. Items 3–4 and 11–13, 16–30 are leads only; I did not complete primary-source verification for them, so they are not findings or rejections.

1. **Examined; defer.** Ransomware backup defense: offline/immutable backups became standard advice; need measured organizational uptake and evidence linking a specific enforced/default shift to outcomes. CISA's #StopRansomware guide is guidance, not adoption: https://www.cisa.gov/stopransomware/ransomware-guide.
2. **Examined; selected.** TLS 1.0/1.1 browser retirement is in the JSON. Firefox 78 shipped the disablement on June 30, 2020, and Chrome 84 removed support after a pandemic delay. Firefox telemetry reported TLS 1.1 on 0.1% of connections in 2018; Chromium documented protocol weaknesses and staged the migration. Browser behavior is the scope; system libraries and legacy services were not universally retired. https://www.firefox.com/en-US/firefox/78.0/releasenotes/ https://hacks.mozilla.org/2020/06/new-in-firefox-78/ https://security.googleblog.com/2019/10/chrome-ui-for-deprecating-legacy-tls.html https://blog.chromium.org/2020/02/
3. Android app permissions: Android 10/11 added one-time permissions and auto-reset for unused apps. Observable OS change; privacy and security motivations mixed. https://developer.android.com/about/versions/11/privacy/permissions.
4. Chrome third-party cookie phaseout: not a security transition; current 2024–25 plans were repeatedly changed. Exclude.
5. **Examined; selected for PyPI.** Registry mandatory MFA: PyPI's all-user requirement is selected; npm's phased top package maintainer requirement is worth a separate follow-up but overlaps supply-chain MFA. https://blog.npmjs.org/post/675982584747327488/changes-to-npm-security-with-two-factor.
6. **Examined; selected for npm token changes.** npm disabled classic token creation, capped new write-token lifetimes, then permanently revoked classic tokens and moved interactive logins to two-hour sessions on December 9, 2025. In July 2026, bypass-2FA tokens also lost the ability to make sensitive account, organization and package changes without an interactive 2FA challenge. The further removal of direct publishing via such tokens is targeted for January 2027 and remains future. https://github.blog/changelog/2025-09-29-strengthening-npm-security-important-changes-to-authentication-and-token-management/ https://github.blog/changelog/2025-12-09-npm-classic-tokens-revoked-session-based-auth-and-cli-token-management-now-available/ https://github.blog/changelog/2026-07-31-restricting-npm-bypass-2fa-granular-access-tokens/
7. **Examined; selected.** 2025–26 Gmail enforcement: verified as actual policy ramp from November 2025; Google FAQ says temporary and permanent rejections. Enforcement began, but no public compliance or rejection rate found: https://support.google.com/mail/answer/14229414.
8. **Examined; defer from public entry.** npm staged publishing is GA as of May 2026, but optional uptake is unmeasured; feature availability alone does not establish a changed common practice. Keep only as an emerging candidate: https://github.blog/changelog/2026-05-29-staged-publishing-and-new-install-time-controls-for-npm/.
9. **Examined; defer.** npm package install script restrictions: controls are offered in 2026 CLI, with no ecosystem-wide default or measured uptake; keep as an emerging option, not established practice.
10. **Examined; ongoing only.** Memory-safe-language migrations: important and industry-wide direction, but public data largely reports organizational strategy and prospective plans. Google says C++ will remain for some uses. Treat as ongoing only, avoid suggesting conversion already happened broadly.
11. QUIC/TLS 1.3: deployment changed network behavior and encrypted more transport metadata, but the security causal chain and comparative prevalence need a separate protocol research pass.
12. DNS over HTTPS: browser defaults changed in some products, but resolver policies and enterprise opt-outs complicate claims of common-practice shift.
13. RPKI/route origin validation: significant deployment progress, but global adoption is partial and requires current measurement from authoritative routing datasets.
14. Passkeys: evidence of high use inside Google accounts but ecosystem-wide use and account coverage remain fragmented; keep partial/adopted, not password retirement.
15. Spectre browser isolation: powerful measurable response, but only selected processes/platforms and costly on memory; hardware mitigations remain separate.
16. Office Internet macros: lead owns it. ActiveX controls in Office are separate and newly documented as disabled by default; assess whether this is sufficiently distinct.
17. Secure Boot: broad consumer inclusion, but adoption differs by device/OS and it does not address all boot-chain compromise.
18. RDP Network Level Authentication: Microsoft recommended it early; need proof of changed defaults and real deployment before selection.
19. SMB signing: Windows 11 Enterprise/Pro changes in 2022–24 make signing required by default in some configurations. Strong potential, but needs current exact edition/build scope and threat evidence.
20. Apple Lockdown Mode: shipped and a concrete defense, but intentionally narrow opt-in population; weaker candidate for a history of common practice.
21. iOS USB Restricted Mode: iOS 11.4.1 (2018) limited USB data after an hour locked in response to forensic unlock tools; evidence of tool arms race and limited consumer scope needed.
22. Chrome/Firefox extension signing: changed ecosystem norms, but Mozilla/Chrome policy timelines and platform-specific exceptions require more complete inspection.
23. Chrome's HTTPS-first/HTTPS-by-default: browsers increasingly auto-upgrade HTTP and warn/block mixed content, while redirects/HTTPS prevalence also reflect Let's Encrypt. Potential sibling to lead's HTTPS entry.
24. Password manager use: advice and browser features spread, but adoption measurement is mixed and not a discrete enforcement/default transition.
25. Credential stuffing breached-password checks: Google and Microsoft add checks, but large-scale impact evidence is hard to isolate.
26. OAuth PKCE: recommended and adopted in native apps, but no single observed global transition; distinguish normative best practice from real ecosystem use.
27. Browser Safe Browsing: defaults/coverage changed over time, yet attribution and comparative outcome evidence are complex.
28. CISA Known Exploited Vulnerabilities catalog: procurement and federal remediation deadlines created an observable prioritization mechanism; use federal-only scope and verify deadlines versus compliance. https://www.cisa.gov/known-exploited-vulnerabilities-catalog.
29. IPv6 adoption and security: not inherently a security improvement; exclude unless a clearly causal practice shift emerges.
30. FIDO security keys in enterprise login: adoption evidence often covers high-risk admins or single employers; Google advanced protection and public-sector mandates may yield bounded cases.

## Recommended shortlist for adjudication

1. SMBv1 removal from clean Windows installs.
2. Exchange Online Basic Auth disablement.
3. Passkey sign-in defaults and measured Google use.
4. GitHub contributor 2FA requirement and enrollment outcome.
5. PyPI mandatory 2FA.
6. IMDSv2's staged transition from feature to selected defaults.
7. Gmail sender authentication requirements and enforcement.
8. Office ActiveX defaults.
9. Chrome Site Isolation after Spectre.
10. npm trusted publishing with OIDC and provenance, described as an available defense with uptake unmeasured.
11. npm classic token revocation, lifetime limits and two-hour sessions (completed 2025 change).
12. TLS 1.0/1.1 browser disablement (2020).
13. Incremental memory-safe language use, marked ongoing and vendor-reported.
14. Android one-time/auto-reset permissions.

These 14 entries favor observable defaults and enforcement. npm staged publishing is deferred because GA alone does not show uptake. The January 2027 plan to remove direct publishing via bypass-2FA tokens remains future and is not counted as completed adoption.
